# target-company-finder 스킬

## 왜 이 방향인가

실제로 채용공고를 보다 보면, 공고 문구와 실제 상황이 다른 경우를 반복해서 마주치게 된다 — 직무기술서(JD)가 실제 업무 범위보다 훨씬 더 많은 역할·역량을 요구하는 경우, "전환형 인턴"이라고 안내해놓고 실제로는 계약 종료로 계속 사람을 교체하고 있는 경우, 회사가 실제로 원하는 사람상과 공고에 적힌 JD 자체가 서로 다른 경우까지. 즉 **공고 문구를 있는 그대로 믿고 거기에 나를 맞추는 접근은, 애초에 신뢰하기 어려운 신호에 최적화하는 셈**이다.

반면 잡플래닛의 **퇴사자 리뷰**는 이런 괴리를 상당히 정확하게 미리 보여주는 경우가 많았고, 사람인의 **연봉 예측 테이블**도 실제 처우와 대체로 맞아떨어졌다 — 공고 문구보다 신뢰할 만한 외부 데이터는 이미 존재한다는 뜻이다. 문제는 그 데이터를 걸러낼 **나만의 정확한 기준점**이 없다는 데 있다.

그래서 이 스킬은 "내가 지원자 입장에서 회사를 일방적으로 따진다"는 목적이 아니라, 공고 문구보다 신뢰할 수 있는 신호들(퇴사자 리뷰, 연봉 데이터, 그리고 나만의 기준)로 먼저 걸러내서, **장기간 다니면서 실제로 성장하고 역경에서 오히려 더 강해지는(antifragile) 회사 핏**을 더 전문적으로 들여다보기 위한 필터로 설계됐다. 이 접근은 신입 채용뿐 아니라 경력직 이직에도 동일하게 적용된다 — 오히려 이미 회사를 몇 곳 겪어본 사람일수록 "나는 이런 환경에서 더 잘한다"는 기준이 더 뾰족해져 있을 가능성이 높다.

## 전체 개요

채용공고 문구를 그대로 믿고 거기에 나를 맞추는 게 아니라 **반대 방향**으로 접근한다. 사용자가 어떤 회사를 원하는지 먼저 역질문으로 구체화하고, 그 기준에 맞는 실제 회사를 리서치로 찾는다 — 이때 공고 문구 자체도 검증 대상이지, 무조건 신뢰하는 출발점이 아니다.

```
Phase 0: 역질문 인터뷰 → 타겟 기업 기준 문서 작성
    └─ [체크포인트] 기준 확정 (사용자가 "됐다"고 할 때까지 역질문 계속)
Phase 1: 기준 기반 실제 기업 리서치
    └─ 후보 기업별 판정(통과/보류/탈락) + 근거 + 출처 URL
Phase 2: 결과 정리 — 우선순위 요약 + 상세 후보 리스트
    └─ (선택) HTML 리포트로 시각화
```

**핵심 원칙**
1. **사용자가 조건을 완벽하게 다 던져줄 거라고 기대하지 않는다.** 방향이 좁혀질 때까지 역질문한다. 반대로 사용자가 처음부터 조건을 스스로 다 던져주는 경우도 있는데, 그럴 땐 역질문 단계를 생략하지 말고 **빠진 카테고리만** 짚어서 추가로 확인한다.
2. **첫 검색 결과를 근거로 결론을 확정하지 않는다.** 특히 "두 직무가 동시에 별도로 채용 중이다" 같은 결정적인 주장은 원문 채용공고를 직접 열어(WebFetch) 재확인한다. 검색 스니펫만 보고 신입/경력, 인턴/정규직을 혼동하는 게 가장 흔한 실패 패턴이다.
3. **검색으로 확인 안 되는 항목은 추측하지 않는다.** 사무실 분위기, 회의 진행 방식, 피드백 스타일, 실제 겸업 허용 여부 같은 건 공개 검색으로 검증 불가능한 경우가 많다 — "직접 확인 필요"로 명시하고 넘어간다.
4. **조사가 여러 라운드에 걸쳐 진행되면, 이전 판정이 뒤집힌 경우 "왜 뒤집혔는지"를 남긴다.** 지우고 새로 쓰지 않는다 — 정정 이력 자체가 사용자에게 유용한 정보다.
5. **직무 타이틀의 의미를 사용자에게 직접 확인한다.** 같은 직무명이어도 회사·업계마다 실제 업무 범위가 다르다. 사용자가 원하는 최종 목표 타이틀과, 그 타이틀에서 빼고 싶은 업무가 충돌하는 것처럼 보이면 지레짐작으로 재정의하지 말고 물어본다.

## Phase 0: 역질문 인터뷰

스킬이 트리거되면 바로 리서치에 들어가지 않는다. 아래 카테고리를 순서대로, **한 번에 다 묻지 말고** 대화하듯 좁혀간다. `AskUserQuestion`을 적극 활용하되, 자유 서술이 필요한 질문은 텍스트로 묻는다.

`references/criteria-interview-guide.md`에 카테고리별 질문 예시가 정리되어 있다 — 그대로 읽어와서 사용자 상황에 맞게 순서·표현을 조정한다.

간단히 요약하면 다음 6개 축을 확인한다:

1. **필수조건(하드 필터)** — 절대 있어야/없어야 하는 조건 (고용형태, 어학 요건, 근무 형태·지역 등)
2. **업종·시장** — 관심 산업/카테고리, "내가 고객이고 싶은" 제품·서비스, 성장성 기준, 전통 대기업 한정인지 신생기업도 포함인지
3. **근무 환경(공간)** — 사무 공간·복지 등 물리적 환경 취향
4. **인적자원/피드백 문화** — 원하는 피드백 방식, 소통 스타일
5. **조직문화** — 성장지향성, 새 제안에 대한 반응 방식, 부서 간 경계 유동성, 겸업 가능 여부
6. **업무 방식/직무 범위** — 가장 놓치기 쉬운 축. 목표 직무 타이틀이 실제로 어떤 업무를 포함하는지 사용자 정의를 먼저 확인하고, 명시적으로 빼고 싶은 업무가 있는지 반드시 확인한다 (예: "마케터"가 콘텐츠 제작·SNS 운영까지 포함하는지, 전략 기획만인지)

각 축을 받을 때마다 다음 축으로 넘어가되, 사용자가 이미 스스로 던진 내용이 있으면 그 축은 건너뛴다. 모든 축이 채워지면 구조화된 기준 문서로 정리해 사용자에게 확인받고, 파일로 저장한다(`references/criteria-doc-format.md` 형식 참고).

**대화 중 모순이 발견되면 임의로 해석하지 말고 되묻는다.** 예: 목표 직무 타이틀 관습상 포함되는 업무를, 사용자가 별개 축에서 "하기 싫다"고 말한 경우 — "이 직무는 보통 OO도 포함하는데, OO는 빼고 싶으신 거면 다른 직무 타이틀도 같이 고려해볼까요, 아니면 이 직무 안에서 OO가 분리된 회사를 찾을까요?" 식으로 선택지를 준다.

## Phase 1: 기준 기반 기업 리서치

### 1-1. 리서치 단위 나누기

Phase 0 기준의 "업종·시장" 축에서 나온 카테고리/세그먼트별로 리서치를 나눈다. 카테고리가 여러 개면 카테고리마다 반복.

병렬 서브에이전트(Task/Agent 도구)를 쓸 수 있는 환경이면, 아래처럼 나눠서 동시에 돌리는 게 효율적이다:
- "기존에 잘 알려진 회사들 검증" 담당 1개
- "신생/성장기업(투자 유치 스타트업 등) 발굴" 담당 1개
- 카테고리가 많으면 카테고리군으로 나눠도 됨

서브에이전트를 못 쓰는 환경이면 순차적으로 WebSearch를 반복한다. 어느 쪽이든 **한 회사당 최소 확인 항목**은 아래 1-2와 동일하게 유지한다.

### 1-2. 회사별 최소 확인 항목

각 후보 기업마다 아래를 확인하고, 확인 안 된 항목은 "미확인"으로 명시한다(추측 금지):

- **필수조건 충족 여부** — Phase 0의 하드 필터 각각에 대해 개별 판정. 특히 어학 요건은 "우대"와 "필수 제출"을 정확히 구분한다 (채용 전형에 관련 시험/면접이 필수 단계로 들어가 있는지 원문에서 확인)
- **직무 범위 부합 여부** — 사용자가 Phase 0에서 정의한 직무 범위와 실제 채용공고의 업무 내용이 일치하는지. "A직무와 B직무가 별도로 분리되어 있다"는 주장은 반드시 두 채용공고 원문을 각각 열어서 고용형태(신입/경력/인턴)까지 대조 확인한다 — 하나가 경력직이고 하나가 인턴이면 "분리 근거"로 쓸 수 없다
- **성장성/시장 신호** — 매출·투자 유치·확장 뉴스 등 실제 수치나 사실 기반 근거
- **문화 신호** — 잡플래닛/블라인드 평점과 실제 리뷰 문구를 함께 확인(평점만으로 판단하지 않는다). 그중에서도 **퇴사자가 남긴 리뷰**가 재직자 리뷰보다 신뢰도가 높은 경우가 많다(재직 중엔 말하기 어려운 내용이 퇴사 후에야 나오는 경우가 흔함) — 가능하면 퇴사자 리뷰를 우선 확인한다. 사용자가 지정한 조직문화 기준(발달지향성, 피드백 방식 등)과 관련된 구체적 리뷰가 있으면 인용한다
- **처우 신호(경력직 이직 시 특히 유용)** — 사람인 등의 연봉 예측 테이블은 실제 처우와 대체로 근접하게 맞는 경우가 많다. 정확한 숫자로 단정하지는 않되, "이 회사가 시장 대비 어느 위치인지" 가늠하는 참고 신호로 활용한다
- **검증 불가 항목 표시** — 사무 공간, 회의 방식, 피드백이 예시 중심인지 등은 공개 검색으로 확인이 안 되는 경우가 대부분이다. 없는 정보를 만들어내지 말고 "커피챗/면접에서 직접 확인 필요"로 남긴다

### 1-3. 판정 라벨

일관된 라벨을 쓴다:

| 라벨 | 의미 |
|---|---|
| **통과 (PASS)** | 확인된 근거로 필수조건·직무범위를 충족 |
| **유력/조건부 (WATCH)** | 구조적으로 맞지만 타이밍(현재 채용 없음 등)이나 일부 항목이 미확인 |
| **불확실 (UNCLEAR)** | 근거가 엇갈리거나 정보가 부족해서 판단 보류 |
| **탈락 (FAIL)** | 필수조건 명백히 위반 (신입 채용 없음, 어학시험 필수, 문화 리스크 명백 등) |

### 1-4. 정정이 필요할 때

이전 라운드에서 통과 판정한 근거가 재조사로 틀렸다고 밝혀지면, 그 항목을 지우지 말고 "정정" 표시와 함께 무엇이 왜 틀렸는지 남긴다. (예: "동시 별도채용"이라던 근거가 실은 경력직 공고 vs 인턴 공고 비교였던 경우 — 실제로 이런 실수가 자주 나온다. 결정적 주장일수록 원문을 다시 열어 재확인하는 습관이 이 실수를 막는다.)

## Phase 2: 결과 정리

`references/candidate-list-format.md` 형식을 기본으로 사용한다. 핵심 구조:

1. **Executive Summary (맨 위)** — 순위별 카드: 1순위 / 조건부 후보 / 하향·보류(정정 이력 포함) / 탈락 확정 / 검증 불가 영역. 사용자가 스크롤 없이 결론만 봐도 되도록 맨 위에 배치.
2. **상세 근거** — 축(필수조건/직무범위/카테고리별/신생기업 등)별로 표 정리, 출처 URL 포함.

### (선택) HTML 리포트

사용자가 시각화를 요청하면:
1. **프로젝트에 이미 디자인 가이드(design-guide.md 등)가 있으면 반드시 그 토큰을 그대로 따른다.** 임의로 새 팔레트/폰트를 만들지 않는다.
2. 없으면 `templates/report.html`의 기본 미니멀 템플릿을 사용한다 (특정 브랜드 톤에 종속되지 않은 범용 스타일).
3. 표가 많은 문서이므로 `overflow-x: auto` 래퍼로 모바일에서도 가로 스크롤이 깨지지 않게 한다.
4. 로컬 파일로 저장 후 기본 브라우저로 열어 확인시켜 준다 (macOS: `open <path>`).

## 트러블슈팅 / 실전에서 확인된 함정

- **채용공고 문구 자체를 곧이곧대로 믿지 말 것.** JD가 실제 업무보다 훨씬 많은 역할을 요구하는 경우, "전환형 인턴"이라고 적혀 있지만 같은 포지션 공고가 주기적으로 반복 게재되는 경우(=매 기수 계약 종료로 사람을 교체하는 구조일 가능성), 회사가 실제로 원하는 인재상과 공고 문구가 다른 경우가 흔하다. 같은 포지션 공고가 반복해서 올라오는지, 퇴사자 리뷰에 "인턴 전환 안 됨"류 언급이 있는지 함께 확인한다.
- **"동시에 별도 채용 중"이라는 결론을 검색 스니펫만 보고 내리지 말 것.** 실제로 경력직 공고와 인턴 공고를 비교해놓고 "직무가 분리돼 있다"고 잘못 판정한 사례가 있었다. 결정적인 주장일수록 원문 공고를 WebFetch로 직접 열어 고용형태를 재확인한다.
- **소규모 스타트업/신생기업은 기본적으로 "직무 미분리" 리스크가 크다는 전제로 접근할 것.** 창업 초기 단계에서는 한 사람이 여러 역할을 겸하는 게 정상이다. "직무가 분리돼 있다"고 판정하려면 실제로 두 개 이상의 별도 포지션이 동시에 열려 있는 근거가 필요하다.
- **어학 요건 문구는 "제출 필수"와 "성적 있으면 우대"를 정확히 구분할 것.** "OO 성적 제출 필요"처럼 애매하게 읽히는 문구는 실제로는 필수인 경우가 많다 — 원문 자격요건 전체를 다시 읽고 면제 조건(해외대학 졸업 등)까지 확인한다.
- **평점만 보고 문화를 판단하지 말 것.** 잡플래닛/블라인드 평점이 같아도 구체적 리뷰 문구(예: "군대문화 잔재", "12~14시간 근무 당연시")가 사용자의 조직문화 기준과 직접 충돌하는지가 더 중요하다. 특히 **퇴사자 리뷰**를 우선 찾아볼 것 — 재직자 리뷰보다 솔직한 내용이 나오는 경우가 많다.
- **사용자가 요청하지 않으면 카테고리를 임의로 좁히지 말 것.** "전통 대기업만"인지 "신생 투자유치 기업도 포함"인지처럼 범위를 넓힐지는 사용자에게 먼저 확인한다.
- **니치한 직군(예: 특정 기술/자동화 전담 직무)을 찾아달라는 요청을 받으면, 시장에 그 직무가 실제로 얼마나 존재하는지부터 정직하게 보고할 것.** 억지로 유사한 직무를 끌어와 "일치한다"고 부풀리지 않는다 — 못 찾았으면 못 찾았다고 말하고, 가장 가까운 대안을 대안으로 명시한다.

## 버전 히스토리

- **v1.2.0**: "왜 이 방향인가"를 "역방향 접근이 방법론적으로 낫다"는 프레이밍에서, "채용공고 문구 자체가 실제와 다른 경우가 많아서(JD가 실제 업무보다 과다 요구, 전환형 인턴 공고가 반복 게재되며 실제로는 계약 종료로 사람을 교체하는 구조, 회사가 원하는 인재상과 JD 불일치) 나만의 기준이 필요하다"는 구체적 이유로 재작성. "안티프래질" 표기를 영문 "antifragile"로 통일. 트러블슈팅에 "채용공고 문구 자체를 곧이곧대로 믿지 말 것" 항목 추가(반복 게재되는 전환형 인턴 공고 패턴 등).
- **v1.1.1**: 신뢰 신호의 출처를 정정 — 잡플래닛은 퇴사자 리뷰(문화 신호), 사람인은 연봉 예측 테이블(처우 신호)로 각각 역할이 다르다는 점을 명확히 구분. 문화 신호 확인 시 재직자보다 퇴사자 리뷰를 우선 찾도록 명시.
- **v1.1.0**: "왜 이 방향인가" 섹션 추가 — 인재상과 실제 조직문화가 어긋나는 경험, 반면 채용 정보 사이트의 데이터는 대체로 신뢰할 만하다는 관찰에서 "나만의 기준점"의 필요성을 정리. 신입뿐 아니라 경력직 이직에도 동일하게 적용된다는 점을 명시하고, Phase 1 확인 항목에 "처우 신호"를 추가.
- **v1.0.0**: 실제 이직 준비 세션에서 여러 라운드에 걸쳐 진행된 워크플로우(역질문 인터뷰 → 기준 문서화 → 다회차 리서치 → 정정 → HTML 리포트)를 일반화해 최초 작성. 회사·직무명이 특정 개인의 실제 지원 이력에 종속되지 않도록 전부 범용 템플릿으로 추상화.
